# VIEW 레지스트리 — 관점(렌즈)을 한곳에 적고, 매번 같은 방식으로 쓰기

터미널에는 볼 게 많다: 매크로 바람, 지수 위치, 추세·모멘텀, 외국인 수급, 옵션, 채권·신용, 일본, 백테스트 결과, 내 규정과 목표.
문제는 **그날 기분에 따라 어떤 날은 수급을, 어떤 날은 차트를 근거로 삼는 것**이다. 그러면 맞아도 왜 맞았는지 모르고, 틀려도 고칠 데가 없다.

이 폴더는 그걸 막는 장부다.

- `views/registry.json` — 렌즈 목록. 렌즈마다 "무슨 질문에 답하나 · 어디서 읽나 · 어떻게 읽나 · 진입/청산/배분에서 어떤 역할인가 · 근거 등급 · 상태"를 적는다.
- `screener/views.py` (`python -m screener.main --mode views`) — 매 실행(장전·장 마감·미장 스크리너) 끝에 모든 렌즈의 현재 상태를 계산해 `reports/views.json` 으로.
- `scripts/view_attribution.py` — PB 판단 기록에 붙은 렌즈 스냅샷으로 "어느 렌즈가 맞았나"를 센다 → `reports/views_attrib.json`.
- 개인 렌즈(내 규정·한도·목표)는 **비공개 저장소** `pb-private/views/personal.json` 에서만 판정한다. 이 공개 저장소엔 id와 역할만 있다.

## 1. 역할 — 렌즈가 판단에 끼어드는 방식 5가지

판단은 세 종류다: **진입(entry)**, **청산·축소(exit)**, **자산배분(allocation)**. 렌즈는 각 판단마다 역할이 따로 있다.

| 역할 | 뜻 (비유) | 허용 조건 |
|---|---|---|
| `gate` 게이트 | 개찰구. 불통과면 그 판단은 안 한다(또는 강제로 한다) | 위험을 **줄이는** 쪽 게이트는 근거 C 이상, 위험을 **늘리는**(매수 허가) 게이트는 B 이상 |
| `weight` 가중 | 저울추. +1(강세)/−1(약세)을 합쳐 기울기를 만든다 | 근거 **B 이상**만 |
| `alert` 주의 | 계기판 경고등. 사이즈를 줄이거나 확인할 걸 늘린다. **방향 결정엔 쓰지 않는다** | 검증 전이어도 가능 |
| `reference` 참고 | 신문 읽기. 알고는 있되 근거로 인용하면 반드시 "(참고)"를 붙인다 | 아무 렌즈나 |
| `none` | 이 판단엔 안 씀 | — |

> 왜 비대칭인가? 틀린 '조심하자' 규칙은 수익을 조금 깎지만, 틀린 '사도 된다' 규칙은 계좌를 깎는다. 그래서 사는 쪽 근거에 더 높은 기준을 둔다.

## 2. 근거 등급

| 등급 | 뜻 |
|---|---|
| A | 결과 보기 전에 정의를 고정(사전등록)했고, 표본 밖(OOS·홀드아웃)에서도 통과 |
| B | 사전등록 비교에서 통계적으로 유의, 또는 내 원장 재생 백테스트에서 큰 차이 (표본 밖 미확인) |
| C | 방향성만 — 표본 작음, 사후 분석, 서술 통계 |
| F | 검증했는데 실패 (효과 없음 또는 반대) |
| 검증전 | 데이터가 없어 아직 못 함 |

등급은 **데이터로만** 올린다. "요즘 잘 맞는 것 같다"는 등급 변경 사유가 아니다.

## 3. 수명주기 — 새 신호·반등 아이디어가 들어오는 길

```
후보 ──(사전등록)──▶ 사전등록 ──(검증 실행)──▶ 검증중 ──(통과)──▶ 채택
  │                                              │                │
  └────────(포기)──────▶ 폐기 ◀──────(실패)───────┘     (성적 악화)▼
                                                                 강등 (참고로만)
```

1. **후보** — 새 아이디어(새 시그널, "이런 반등 패턴이 보인다", 뉴스에서 본 지표)는 언제든 넣는다. 단:
   - `status: "후보"`, 모든 역할 `none` (= **가중 0**). 판단에 영향 없음.
   - `history` 에 날짜·가설 한 줄. `review_by` 는 2~4주 뒤.
   - id는 `cand.` 으로 시작하면 구분이 쉽다.
2. **사전등록** — 결과 보기 전에 정의를 고정: 이벤트 정의, 비교 기준, 보유기간, 판정 규칙. `screener/lab.py` 레지스트리나 `reports/studies/*.md` 0절처럼 **커밋으로 남긴다**. 커밋 뒤엔 정의를 바꾸지 않는다(바꾸면 새 후보).
3. **검증중** — lab/스터디 실행. 결과가 나오면 등급을 매긴다.
4. **채택** — 등급이 역할 조건(1절 표)을 만족할 때만 gate/weight 로 올린다.
5. **강등** — 채택 후 성적이 나빠지거나(귀속 n ≥ 20에서 적중률 50% 미만 등), 재검증에서 F → 역할을 `reference` 로 내린다. 지우지 않는다(무엇이 틀렸었는지가 기록).
6. **폐기** — 데이터를 영영 못 구하거나 의미가 없어진 것.

### 규칙 3개 (흔들림 방지)
- **렌즈당 주 1회 변경**: 같은 렌즈의 역할·등급·상태는 7일 안에 두 번 못 바꾼다. (`views.py` 가 `lint` 에 표시)
- **재검토 기한**: `review_by` 가 지나면 `lint` 에 뜬다. 지난 렌즈는 다음 주간 리뷰에서 결론을 낸다.
- **역할-등급 불일치 금지**: F·검증전 렌즈가 gate/weight 면 `lint` 에 뜬다. 고칠 때까지 그 판단의 근거로 인용 금지.

## 4. 이벤트 예외 (override) — 반드시 만료일

서킷브레이커 날, 일본은행 깜짝 발표, 전쟁 같은 일이 생기면 렌즈를 고치는 대신 `registry.json` 의 `overrides` 에 **임시 규칙**을 넣는다.

```json
{"id": "ovr-YYYY-MM-DD-이름", "scope": "entry|exit|allocation|all", "effect": "alert",
 "line": "화면에 뜰 한 줄", "why": "근거 (검증 아님이면 그렇게 적기)", "created": "YYYY-MM-DD", "expires": "YYYY-MM-DD"}
```

- `expires` 없으면 **무효**(lint 경고). 최대 10거래일 권장.
- 만료 후에도 계속 필요하면 → 그건 이벤트가 아니라 새 렌즈 후보다. 3절 경로로.

## 5. 리뷰 주기

| 언제 | 무엇을 |
|---|---|
| 매 실행 | `reports/views.json` 자동 갱신. 게이트가 뒤집히거나 새 주의가 뜨면 운용회의 텔레그램에 한 줄 |
| 매주 일요일 (성적표와 함께) | `lint` 확인, 후보 정리(사전등록할 것 / 버릴 것), 이벤트 예외 만료 확인, `views_attrib.json` 훑기 |
| 매월 | 등급 재평가 — lab·스터디·귀속 결과로만. 바꾼 건 `history` 에 날짜·이유 |
| 분기 | 개인 규정(rules.txt) 리뷰 때 personal 렌즈 역할 재검토 |

## 6. PB 판단에서 쓰는 법 (순서 고정)

1. `summary.<판단>.gates` + 개인 게이트(`pb-private/views/personal.json`) — 하나라도 **불통과면 그 판단은 하지 않는다.**
2. `summary.<판단>.tilt` — B 이상 렌즈의 기울기. 진입 크기·타이밍에만 쓴다.
3. `summary.<판단>.alerts` — 사이즈 축소·확인 항목. 방향 근거로 쓰지 않는다.
4. `reference` — 설명엔 써도 된다. 단 "(참고, 등급 X)"를 붙인다.
5. 판단을 기록하면(`record_pb`) 그 순간 렌즈 상태가 자동으로 `pb_view.lenses` 에 붙는다 → 나중에 귀속.

## 7. 새 렌즈 추가 체크리스트

- [ ] 계산이 필요하면 `screener/views.py` 의 `EVAL` 에 판독 함수 추가 — 입력이 없으면 `NA()` 반환, 예외는 views.py가 잡는다
- [ ] 임계값은 코드가 아니라 `read.params` 에 (레지스트리가 단일 출처)
- [ ] 개인 정보(보유·수량·금액·개인 한도 수치)는 절대 이 파일에 넣지 않는다 → `personal` 계열은 pb-private
- [ ] `python -m screener.views` 로 `lint` 가 비었는지 확인
